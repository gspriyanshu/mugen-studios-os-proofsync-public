The short answer

What inventory work should remain possible offline?

Technicians should be able to see the assigned job and relevant stock, record controlled issue, use and return events, capture an exception and understand what is pending synchronization. Conflict behavior must be tested, not assumed.

What this cannot decide

The fictional interface has no offline or synchronization capability.

01

Cache the technician's working set, not the entire warehouse

Offline access should include assigned jobs, required parts, current vehicle stock and the reference details needed to complete those jobs. Downloading an unrestricted enterprise catalogue adds delay and exposes data the technician may not need.

The working set needs a visible freshness marker. A technician should know when the job and stock snapshot last synchronized, especially before promising a substitution or additional part.

02

Queue field events with stable identifiers

Part usage, returns, photographs and checklist completion should be saved locally as discrete events with client-generated identifiers. When connectivity returns, retries must not create duplicate consumption simply because the first acknowledgement was lost.

The interface should distinguish saved-on-device, queued, synchronized and rejected states. A green completed job should not hide an inventory event that failed validation after reconnection.

03

Design conflict resolution before deployment

Two technicians may act on the same apparent stock or a dispatcher may reassign a job while one device is offline. The product needs a stated rule for which fields merge, which events remain additive and which conflicts require human review.

Testing should cover clock drift, repeated reconnects, partial uploads and device replacement. Offline capability is credible only when the team can recover from interrupted synchronization without losing the audit trail.
