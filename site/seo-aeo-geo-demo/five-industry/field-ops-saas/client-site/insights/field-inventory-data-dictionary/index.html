The short answer

What belongs in a field-service inventory data dictionary?

Define each location, item, quantity, unit, event, job reference, actor, timestamp, source system, reason, cost treatment and exception state so operations, finance and integrations use the same meaning.

What this cannot decide

A qualified operations, accounting and technical review is required before a real data contract is approved.

01

Define nouns before events

A shared dictionary begins with stable identities for part, location, vehicle, technician, work order and serviced asset. If branch codes or units of measure differ between systems, every downstream event can look valid while describing a different thing.

Each noun needs an authoritative system, human owner and change rule. Aliases can support search, but the event record should retain the canonical identifier used for reconciliation.

02

Model movement as immutable business events

Receipts, reservations, issues, transfers, consumption, returns, damage and count adjustments describe why balances change. Storing the event identity, source, destination, quantity, unit, actor and time makes the balance explainable.

Corrections should reference the original event instead of erasing it. That allows an auditor to reconstruct what was first recorded, what changed and who approved the correction.

03

Attach quality rules to every field

A field definition is incomplete without allowed values, null behavior and validation timing. For example, a destination location might be optional for consumption but mandatory for a transfer.

Quality monitoring should distinguish missing data from contradictory data. A blank serial number and the same serial assigned to two installed assets are different failures and should reach different owners.
